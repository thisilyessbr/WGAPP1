# Relayqo audit — 13 September 2026

## Fix update

The five findings below are retained as the original audit record. Fixes have now been implemented:

- Durable queue insertion is the webhook deduplication authority. Failed inserts remain retryable; existing rows are acknowledged.
- Claim transactions are serialized briefly; leases renew during execution, outbound delivery checks ownership, and state writes include worker and claim generation. Expired SENDING jobs and network-uncertain deliveries are held as UNKNOWN for manual reconciliation rather than resent blindly.
- Safety lookup failures throw and enter queue retry handling.
- Channel permissions apply only to channel routes; ordinary chat retains customer authorization.
- Human takeover state and legacy flags are updated in one transaction; resume clears active handoff status without reopening completed conversations.
- Shutdown drains HTTP and queue work before disconnecting the database. Provider HTTP calls have a 15-second timeout.

Validation: production build/typecheck pass. Focused unit regressions pass. An initial database run passed 41/41 safety, remediation and durable queue tests, including stale-worker fencing and uncertain-delivery recovery. A subsequent run adding heartbeat/shutdown coverage suffered local database connection termination and leftover test jobs, so that later run is not a clean verification result. A reliable PostgreSQL heartbeat/shutdown run and live Meta send/receive test remain release checks. No production deployment or real message was performed.

UNKNOWN jobs require checking provider delivery before an operator explicitly retries; no automatic reconciliation UI was added. These protections reduce duplicate risk but cannot make a remote send and a local database commit atomic.

## Verdict

Not ready for production sign-off. The production build passes, but five actionable runtime defects remain. The earlier statement that the project was code-ready was premature.

This review inspected the current workspace backend: application mounting, authentication, webhook ingestion, durable queue, outbound routing, conversation safety, build and deployment configuration. It did not reverify live Meta settings, deployed backend infrastructure, production credentials or live message delivery. No application fixes were made in this audit; only this report and defect reproduction tests were added.

## Findings

### P1 — Incoming messages can be lost on a transient database error

Location: `src/domain/channel/whatsapp/WhatsAppWebhookRouter.ts:85`, `:116`, `:131`.

The webhook records the deduplication key before resolving the number and enqueueing the job. When enqueue throws, the outer catch returns 500 without removing that key. The retry returns 200 with zero processed messages because it sees a duplicate. The production queue throws on non-uniqueness database failures, so this is a reachable error path.

Reproduced with a correctly signed webhook: first response 500, retry 200/processed=0, enqueue called only once. Make durable insertion the deduplication authority or atomically coordinate receipt and job insertion; account for crashes between steps, not only thrown exceptions.

### P1 — Expired queue leases allow overlapping processing and stale writes

Location: `src/domain/channel/whatsapp/MessageQueue.ts:166`, `:232`, `:292`, `:319`.

Jobs are reclaimable after 60 seconds with no heartbeat. Completion and failure writes select only job ID and do not verify the current worker or lease generation. A slow worker can continue after another worker reclaims its job, send another response, and overwrite the newer worker's state. Outbound HTTP calls have no explicit timeout. The new conversation-level in-flight map only covers one engine instance and does not deduplicate provider sends.

Confirmed the missing lease ownership predicate with a focused reproduction. A real multi-worker PostgreSQL race was not run in this review. Add renewable leases, fencing for state writes, bounded network calls, and explicit handling for uncertain provider delivery.

### P1 — Safety lookup errors can permit sending

Location: `src/domain/channel/guard/ClientSafetyGuard.ts:179`, `:233`.

Errors reading tenant pause configuration or resolving the conversation are logged and ignored. If later routing succeeds, the reply can be delivered without establishing whether automation was paused or handed to a human.

Reproduced: both database reads throw and the guard returns allowed=true. Treat unavailable safety state as a retryable failure and defer delivery until it can be checked.

### P1 — Channel admin middleware blocks ordinary chat users

Location: `src/app.ts:109`.

The channel router is mounted with requireAuth and requireAdmin over all of `/api/v1` and `/api`, before the ordinary API router. A valid customer-scoped user token for `/api/v1/chat` is rejected with the channel-management administrator error before the chat route runs. Existing API code explicitly supports customer-scoped principals.

Reproduced against createApp with channel services present: HTTP 403. Scope channel administration checks to the channel-management routes and retain the chat route's own customer authorization.

### P2 — Resume bot does not clear HUMAN_ACTIVE status

Location: `src/domain/channel/guard/ClientSafetyGuard.ts:422`.

setHumanTakeover(false) enables bot automation and clears humanRequested, but leaves Conversation.status=HUMAN_ACTIVE. The guard and conversation engine still suppress the reply based on that status. The UI can report resumed while the bot stays silent.

Reproduced by resuming a HUMAN_ACTIVE conversation and evaluating the guard: botEnabled=true but HUMAN_TAKEOVER is returned. Reconcile the legacy status with the automation state atomically, without reopening completed conversations inadvertently.

## Verification and limits

- `npm run build`: passed, including Prisma generation and production TypeScript compilation.
- Four focused test files: 21 assertions passed. Of these, five deliberately reproduce defects and assert the observed broken behavior; they are evidence, not a clean readiness gate. Convert these to desired-behavior regression tests when fixing the issues.
- Existing security boundaries, secret encryption and channel routing checks in that run: 16 passed.
- The full integration suite was not rerun; prior full-suite failures are not resolved or waived by this focused run.
- Previous migration replay and live website checks were not repeated in this audit.
- No production database operations, real messages, deployment, or Meta account mutations were performed.

Additional operational concern: shutdown disconnects Prisma and exits without first draining the HTTP server and message queue (`src/app.ts:172`). Deployment during delivery can interrupt a job after sending but before completion is recorded. Include shutdown and retry behavior in the deployment rehearsal.

## Release gate

Fix the five findings, rerun the reproductions as desired-behavior tests, verify queue expiry and shutdown against real PostgreSQL with multiple workers, and run a live single-number send/receive/retry test on the permanent backend before onboarding paying clients. Build success alone is insufficient.
